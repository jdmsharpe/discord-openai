## Provider notes

### Sampling parameters on reason-by-default models

- **Models that reason when no effort is sent reject sampling parameters too (fixed 2026-09-22).** `REASONING_BY_DEFAULT_MODELS` in `discord_openai.util` (`gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`/`-terra`/`-luna`, `gpt-5.5`) reason at medium when the request omits `reasoning.effort`, and a probe on 2026-09-22 returned 400 `Unsupported parameter: 'temperature'` for `temperature=0.5` with no reasoning param on each of them; they accept it only at an explicit effort `none`. `ResponseParameters.__init__` now drops `temperature`/`top_p` for them when the effort is omitted (the existing rules for effort != `none` and for pro mode without an effort are unchanged). Until then `/openai chat model:gpt-5.6-sol temperature:0.5` with no effort sent the parameter and failed; the four Pro tiers failed the same way and moved to `NO_SAMPLING_MODELS`. `gpt-5.4` / `5.4-mini` / `5.4-nano` / `5.2` / `5.1`, `gpt-4.1` / `4.1-mini` and `gpt-4o-mini` accept `temperature` with no effort and are in neither set. Guard: `TestSamplingParametersWithoutEffort` in `tests/test_util.py` (set pins plus per-model payload cases).

### Reasoning effort gate

- **Reasoning effort is gated per model before the request.** `SUPPORTED_REASONING_EFFORTS` in `discord_openai.util` maps every reasoning model in `CHAT_MODEL_CHOICES` (plus the research ids) to its live-probed effort set — probed 2026-07-13 (5.6 `minimal`), 2026-08-28 (the rest) and 2026-09-15 (GPT-6 Astra) with the bot's own payload and `max_output_tokens=16`, plus 2026-09-22 (GPT-6 Sol/Luna) and 2026-10-08 (GPT-6.1 Sol): GPT-6 Astra and GPT-6.1 Sol take `low`/`medium`/`high`/`xhigh`/`max` (reject `none` and `minimal`); GPT-6 Sol/Luna and GPT-5.6 Sol/Terra/Luna take `none`/`low`/`medium`/`high`/`xhigh`/`max` (reject `minimal`); GPT-5.5/5.4/5.4 Mini/5.4 Nano/5.2 take `none`..`xhigh`; GPT-5.1 `none`..`high`; GPT-5/5 Mini/5 Nano `minimal`..`high` (reject `none`); GPT-5.5 Pro/5.4 Pro/5.2 Pro `medium`/`high`/`xhigh`; GPT-5 Pro `high` only; o3/o3 Pro `low`/`medium`/`high`. `reasoning_effort_error()` turns an unsupported menu combination into a friendly error embed in `run_chat_command` instead of a raw 400; unmapped ids (GPT-4.1, GPT-4o Mini, un-probed o-series) pass through unvalidated. Guards: `TestSupportedReasoningEfforts` in `tests/test_util.py` (exact map pin + accept/reject cases) and `test_every_menu_reasoning_model_has_an_effort_entry` in `tests/test_openai_cog.py` — adding a reasoning model to the menu requires probing each effort and adding its row.

### Pro reasoning mode

- **Pro reasoning mode is an opt-in `/openai chat` option (`reasoning_mode`), gated per model before the request.** `PRO_MODE_MODELS` in `discord_openai.util` is the live-probed set (2026-08-28, 2026-09-15, 2026-09-22 and 2026-10-08, bot payload): GPT-6 Astra/Sol/Luna, GPT-6.1 Sol (~1,470 extra input tokens) and GPT-5.6 Sol/Terra/Luna accept `reasoning.mode = "pro"` with any effort (`none`..`max`) or none at all; `gpt-5.5` returns a 400 `unsupported_value` on `reasoning.mode`; `gpt-5.5-pro` accepts it as a no-op and is excluded on purpose. `reasoning_mode_error()` runs before `reasoning_effort_error()` in `run_chat_command` and refuses `pro` on every other model via the error embed (it lists the seven ids); an unset mode and `standard` always pass. `build_reasoning_config(model, reasoning_effort, reasoning_mode)` in `responses.py` emits `{"summary": "auto", "mode": "pro"}` plus `effort` only when one was chosen, and **never emits `mode: "standard"`** — the key is omitted so models that reject it never see it. Temperature rule: pro with no explicit effort reasons at the API default (medium) and 400s on `temperature`/`top_p` (`Unsupported parameter: 'temperature'`), so `ResponseParameters.__init__` drops both; pro with effort `none` keeps them. Mode and effort are independent, and the cost is plain inflated standard usage (~1.5k fixed input tokens per call, roughly 4-6x per turn, tool schemas and history multiplied) that `extract_usage` already captures, so pricing.yaml and `calculate_cost` are untouched. The intro embed appends `**Reasoning Mode:** pro`. Guards: `TestReasoningModeError` (exact set pin, accept/reject cases) and `test_pro_mode_without_effort_strips_temperature` / `test_pro_mode_with_effort_none_keeps_temperature` in `tests/test_util.py`; `TestBuildReasoningConfig` in `tests/test_openai_responses.py`; `test_chat_command_rejects_pro_mode_on_unsupported_model_before_request` and `test_chat_command_sends_pro_mode_and_renders_it` in `tests/test_openai_chat.py`; `test_reasoning_mode_choice_set` in `tests/test_openai_cog.py`. Adding a model to `PRO_MODE_MODELS` requires probing `mode: pro` on it first and updating the pin.

### Cached-input rates

- **Cached-input rates must be declared per model, never inferred.** The published discount varies by generation — 90% off for the gpt-5 and gpt-6 families (95% off for gpt-6.1-sol: its model page prices cached input at "5% of the uncached input token rate"), 75% off for gpt-4.1/o3/o4-mini, 50% off for gpt-4o/o1/o3-mini — so the 50% fallback in `calculate_cost` is wrong for most of the catalog and has silently misbilled twice (5× on gpt-5, 2× on gpt-4.1/o3). Every model with a published rate carries `cached_input_per_million` in pricing.yaml; the only ids allowed to reach the fallback are the Pro tiers and legacy models that genuinely publish none. Two guards pin this: `test_declared_cached_rates_match_published` (rate == input × expected discount) and `test_every_model_declares_or_is_exempt` (no model may silently rely on the fallback). When adding a model, look up its cached rate — a deprecated id still has one on its own model page even when the aggregate pricing table omits it. GPT-5.6 additionally bills **cache writes** (`usage.input_tokens_details.cache_write_tokens`, populated on first-turn requests) at 1.25× the uncached input rate: `cache_write_per_million` is declared on the GPT-6, GPT-6.1 and GPT-5.6 rows only (every other row prints `-` in the table's Cache-writes column, so `calculate_cost` bills their cache-write tokens as ordinary input), and ordinary input = input − cached − cache_write, never negative. Guards: `test_gpt_5_6_cache_write_rates_are_125_percent_of_input` (declared set == gpt-6 / gpt-6.1 / gpt-5.6 rows — the `gpt-6` prefix covers `gpt-6.1-sol` — rate == 1.25× input) plus the `test_calculate_cost_cache_write_*` cases in `tests/test_util.py`; `extract_usage` reads the field defensively (`test_older_usage_shape_without_cache_write_field`) and the value is stored as `cache_write_tokens` in `UsageInfo`/`PendingMcpApproval` and passed to `track_daily_cost` and the pricing embed.

### Long-context tier

- **Long-context tier (v1.11.0):** GPT-5.4 / 5.4 Pro / 5.5 / 5.5 Pro, the GPT-5.6 trio and the GPT-6 models bill the WHOLE request at 2x input / 2x cached / 2x cache-write / 1.5x output once the prompt exceeds 272K input tokens (pricing page tooltips "Short context <=272K" / "Long context >272K"; model pages: "for the full session"). Declared as a `long_context` block per row in `pricing.yaml` (`threshold_tokens: 272001` — 272K is assumed to be 272,000, matching colmad), loaded into `LONG_CONTEXT_PRICING` and applied in `calculate_cost` when `input_tokens >= threshold_tokens`; a tier without a cached / cache-write rate falls back to 50% of the tier input / the tier input, the same fallback as the base tier. Pinned by `test_long_context_tiers_are_pinned` (`tests/test_config_pricing.py`) and the `test_long_context_tier_*` cases in `tests/test_util.py`. Caveat: `input_tokens` is one response's prompt count except on the MCP-approval continuation path, which sums two responses' usage before costing, so a summed prompt could cross a threshold neither request did. Found by the colmad parity check (colmad had carried the tiers since 2026-08-28).

### Fast mode

- **Fast mode (v1.12.0, `/openai chat service_tier`):** OpenAI's Fast mode (Priority processing renamed 2026-07-30) is requested with `service_tier: "fast"` (the API also takes `"priority"`; the RESPONSE reports `"priority"` on GPT-5.6 and earlier and `"fast"` on the GPT-6 models, and `FAST_SERVICE_TIERS` covers both) and billed at the pricing page's "Fast mode" tab rates — 2x standard for the GPT-6 models and the GPT-5.6 trio, other multiples elsewhere. Those seven fast rows (GPT-6 Astra/Sol/Luna, GPT-6.1 Sol, the GPT-5.6 trio) also publish a long-context tier (2x the standard long-context rates above 272K input tokens; the GPT-5.5 / 5.4 fast rows stay flat), stored as `fast.long_context` in `pricing.yaml` → `FastTier["long_context"]` and applied by `calculate_cost` before the flat fast rate (v1.13.0; until then fast long prompts billed the flat fast rate). Declared as a `fast` block per row in `pricing.yaml` → `FAST_TIER_PRICING` (`FastTier`), applied in `calculate_cost(..., service_tier=...)` when the tier is in `FAST_SERVICE_TIERS` (`{"fast", "priority"}`), overriding the long-context tier; `extract_usage` reads `response.service_tier` (None when absent or not a string) into `UsageInfo["service_tier"]`, and every `track_daily_cost` / `append_pricing_embed` / `_append_public_pricing_embed` call passes it through (the embed appends "fast mode"). `SERVICE_TIER_CHOICES` follows the `reasoning_mode` pattern: `standard` is never sent, `fast` is stored on `ResponseParameters.service_tier` and sent on every turn; `service_tier_error()` rejects `fast` on any model without a fast row (Pro tiers, o1/o3-mini, legacy) before the request. `ultrafast` is deliberately not offered. Since 2026-10-08 it is GA and priced at 6x standard for `gpt-6-astra` ($60 / $6 cached / $75 cache-write / $300 per 1M) and `gpt-6.1-sol` ($12 / $0.60 / $15 / $60), and the response reports `"ultrafast"` (probed 2026-10-08); `gpt-6-sol` returns 400 `Invalid service_tier argument`, and GPT-6 Luna and GPT-5.6 have no ultrafast row. pricing.yaml carries no ultrafast block and `FAST_SERVICE_TIERS` does not include it, so a response reporting `"ultrafast"` (for example from a project default) is billed at standard rates. Offering it would need an `ultrafast` pricing block, a gate like `service_tier_error`, and a choice entry. Pinned by `TestFastTiers` (`tests/test_config_pricing.py`), the `test_fast_tier_*` / `TestServiceTierError` / `test_service_tier_*` cases in `tests/test_util.py`, and the three `test_chat_command_*fast*` / `*standard_tier` cases in `tests/test_openai_chat.py`; the chat option count pin is now 15.

### Image cost

2026-11-10: [OpenAI deprecations](https://developers.openai.com/api/docs/deprecations) adds `gpt-image-2` and its dated snapshot retirement on 2027-02-10, with the 2.6 pair as replacements. The existing 1.5 / 1-mini retirement remains 2026-12-01.

- **Image cost is billed from the response's token usage (v1.13.0).** OpenAI bills GPT Image models per token and the Images API reports the usage on every response (`usage.input_tokens_details.text_tokens` / `image_tokens`, `usage.output_tokens_details.image_tokens`); `calculate_image_cost_from_usage(model, response.usage)` prices them with `IMAGE_TOKEN_PRICING` (the `per_million_tokens` block of each `image_generation` row: $5 text in / $8 image in / $30 image out on GPT Image 2 and 2.5, $32 out on 1.5, $10 in / $40 out on 1, $2 / $2.50 / $8 on 1-mini). The per-image table is now only the fallback (`calculate_image_cost`, keyed by the quality and size the response echoes). Motivation: an `auto` request resolves server-side to `low` at a non-standard size (1312x1199, 215 tokens, $0.0065 on 2026-09-15) while the old flat `default_per_image` billed $0.053 — a 9x over-estimate on every default call. GPT Image 2.6 Sunburst (default since the 2026-11-06 sweep) and Flare lead `IMAGE_MODEL_CHOICES`, followed by the 2.5 pair (7 of 25); `xhigh` / `max` qualities are gated by `image_quality_error` (`EXTENDED_IMAGE_QUALITY_MODELS`, the 2.5 and 2.6 pairs) because gpt-image-2 400s `does not support quality 'xhigh'` (probed 2026-09-15); their per-image rows come from OpenAI's calculator and were confirmed at low / medium / high by live generations; Batch is not supported on 2.5. Pinned by `TestImageCostFromUsage` and `TestImageQualityGate` (`tests/test_util.py`), `test_image_token_rates_are_pinned` and `test_gpt_image_2_5_per_image_rows` (`tests/test_config_pricing.py`).

### STT deprecation

- **STT deprecation (announced 2026-08-26):** `whisper-1`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe` and `gpt-4o-transcribe-diarize` shut down on **2027-02-26** (replacements `gpt-transcribe` / `gpt-live-transcribe`). ### Per-user safety identifier

- **Per-user safety identifier (keyed since 2026-10-08).** `build_safety_identifier(user_id)` in `discord_openai.util` returns `HMAC-SHA256(key, str(user_id)).hexdigest()` (64 lowercase hex chars, untruncated). The key is `SAFETY_IDENTIFIER_SECRET` (UTF-8) when set, otherwise `HMAC-SHA256(BOT_TOKEN, b"safety-identifier-v1")` (`derive_safety_identifier_key`, computed once at import into `SAFETY_IDENTIFIER_KEY`); with neither set it returns `None` and no identifier is sent. The OpenAI API key is never key material, because OpenAI holds it and could rebuild the mapping by hashing known Discord IDs. Until this change `hash_user_id` sent the unkeyed `sha256(str(user_id))[:16]`, which OpenAI could match by hashing known Discord IDs. Where it is sent: `safety_identifier` on `responses.create` for chat (`ResponseParameters`, so every follow-up and MCP-approval turn too) and research (`ResearchParameters`); `user` on `images.generate` and `images.edit` (`ImageGenerationParameters.user`; the Images API has no `safety_identifier` field in openai 3.31.0). `audio.speech`, `audio.transcriptions` and `audio.translations` accept neither field (SDK 3.31.0 signatures), so TTS and STT send nothing. Length: the Responses API reference gives a 128-character maximum for `safety_identifier` (https://developers.openai.com/api/reference/resources/responses/methods/create), and the SDK docstring says the same since openai 3.29.0 (64 before); the images `user` field documents no maximum (https://developers.openai.com/api/reference/resources/images); the guide (https://developers.openai.com/api/docs/guides/safety-best-practices#implement-safety-identifiers) gives none. Probed 2026-10-08 on `gpt-6-luna` (effort `none`, bot payload): a 64-hex value and a 65-character value both returned 200. Changing the secret, or `BOT_TOKEN` when no secret is set, changes every user's identifier. Guards: `TestSafetyIdentifier` / `TestDeriveSafetyIdentifierKey` in `tests/test_util.py`, the `SAFETY_IDENTIFIER_SECRET` cases in `tests/test_config_auth.py`, and `tests/test_safety_identifier.py` (identifier present and raw ID absent in each request body). `validate_required_config` refuses to start when `SAFETY_IDENTIFIER_SECRET` equals `OPENAI_API_KEY`, without printing either value (`tests/test_config_auth.py::test_validate_required_config_rejects_the_api_key_as_safety_secret`); discord-grok and discord-openrouter carry the same check.

> 2026-11-06: since the 2026-10-28 sweep, `images.generate` and `images.edit` send `safety_identifier` (`ImageGenerationParameters.safety_identifier`), not `user`.

### Connector presets on GPT-6 models

- **Connector presets are refused on the GPT-6 models (2026-09-22).** An `mcp` tool carrying `connector_id` returns 400 `Built-in MCP connector 'dropbox' (connector_id) is not supported with this model. Remove the connector tool or use a supported remote MCP integration.` on gpt-6-astra, gpt-6-sol and gpt-6-luna (probed 2026-09-22) and on gpt-6.1-sol (2026-10-08); gpt-5.6-sol and gpt-5.4-nano pass that check. SDK 3.16.0 deprecates `connector_id` for every model released after 2026-09-01. `mcp_connector_error(model, presets)` in `config/mcp.py` refuses any `kind="connector"` preset on `CONNECTOR_UNSUPPORTED_MODELS` and names the alternatives (a `remote_mcp` preset, or GPT-5.6 or earlier); `resolve_selected_tools()` calls it after `resolve_mcp_presets()`, which covers the chat start, the tool selector and follow-up turns. Remote MCP presets are unaffected. Guards: `TestMcpConnectorError` in `tests/test_openai_mcp_config.py`, `test_resolve_selected_tools_refuses_connector_preset_on_gpt_6` in `tests/test_openai_tooling.py`, and `test_chat_command_rejects_connector_preset_on_default_model_before_request` in `tests/test_openai_chat.py`.

### Stickers are sent as text

- **Stickers are sent as text (v1.16.1).** A Discord sticker arrives with empty `content` and no `attachments`; `handle_new_message_in_conversation` (`chat.py`) sends each sticker in `message.stickers` as a `[Sticker: <name>]` line after the message text, built by `text_with_stickers` in `stickers.py`, which is byte-identical in the five AI bots (change all five together). The sticker image is not sent. A follow-up with nothing to send (no text, no sticker, no attachment that yields content) is ignored and the conversation stays open. Before, discord-openai, discord-gemini and discord-claude sent an empty turn, got a 400, and the error path removed the conversation; discord-grok and discord-openrouter dropped a sticker-only message without a reply. Pinned by `tests/test_stickers.py` and the sticker follow-up tests in `tests/test_openai_chat.py`.

### Attachments and generated audio stay in memory

- **Attachments and generated audio stay in memory (2026-10-08).** `fetch_attachment_bytes(url)` in `discord_openai.util` returns the attachment's bytes; STT, translation and image edit send them as `(filename, bytes)` tuples, and the STT and TTS replies attach a `BytesIO` (TTS uses `response.content`). Nothing is written to disk. Before, `download_attachment` wrote every attachment to `tempfile.gettempdir()/<attachment filename>` and TTS wrote `gettempdir()/<voice>_speech.<format>`, so two users sending a Discord voice message (always named `voice-message.ogg`) at the same time, or two TTS requests with the same voice and format, could read or delete each other's file. Guard: `tests/test_attachment_bytes.py` (`TestSpeechToText`, `TestTextToSpeech`, `TestImageEdit`; the temp and working directories are read-only there, so any file write fails the test).

### Slash-command choice cap

From the CLAUDE.md Gotchas section:

- **Slash-command options cap at 25 static `choices`.** Discord rejects any option with >25 entries (error `50035`), and py-cord's startup sync is one all-or-nothing bulk `PUT` — so a single over-limit list (most likely a model menu in `command_options.py`) aborts command registration for **every** cog inside `on_connect`, surfacing only as `Ignoring exception in on_connect`. `CHAT_MODEL_CHOICES` is at 25 of 25 (GPT-6.1 Sol added at the 2026-10-08 sweep, GPT-6 Sol and Luna at the 2026-09-22 sweep, GPT-6 Astra in v1.13.0, GPT-5.6 Sol/Terra/Luna in v1.6.0, into room pre-cleared by the v1.5.0 prune), so no slot is left; before adding another model, drop a deprecated one (the 2026-12-11 batch: `gpt-5`, `gpt-5-mini`, `gpt-5-nano`, `gpt-5-pro`, `o3`, `o3-pro`) or — to escape the cap permanently — switch that option from `choices=` to an `autocomplete=` callback (no length limit). `REASONING_MODE_CHOICES` (2 entries, v1.10.0) is picked up by the same `tests/test_choice_caps.py` discovery. Separately, Discord caps a command at 25 **options**: `/openai chat` carries 15 (pinned by `test_reasoning_mode_option_is_on_chat_and_pro_models_are_menu_selectable` in `tests/test_openai_cog.py`), and every subcommand's serialized payload must stay under 8000 bytes (`test_registered_command_groups_fit_discord_size_limit`).

> 2026-11-06: `gpt-5-nano` left `CHAT_MODEL_CHOICES` at the 2026-10-28 sweep (its slot went to `gpt-6.1-terra`), so it is no longer one of the deprecated ids that can be dropped to make room.
